# Magic SQD Mobile — Android-спайк

Отдельный проект, полностью независимый от десктопной версии в `app/`/`cars/`/
установщиков в корне репозитория. Ничего из существующих PC-файлов не
изменяется и не импортируется напрямую — при переносе логики файлы
копируются/переписываются заново под Android-окружение, а не редактируются
in-place.

libaums `UsbFile`, но сама последовательность reboot→wait_device→продолжение,
`{ask}`-подстановка и реальная запись на флешку — первое, что нужно
проверить на живом железе).

**Полный прогон реальной сложной модели** (Haval M6 "до 04.2026", 8 этапов,
без сокращений) — без единого падения:
`check`(выбор версии прошивки, "1") → `usb`(**корректно СКРЫТ**, т.к.
condition_var/condition_values не совпали с выбором "1" — первое реальное
подтверждение ветвления по check_var/condition_var) → `adb`(11 команд:
`#root`/`#sleep`/`#disable_verity`/`#remount` вперемешку с сырыми
`mkdir`/`cp`/`mv`/`ln -s`/`chown`/`chmod`/`find … -exec`/`rm -rf` и
`#reboot_nowait` в конце — все корректно распарсены и отрендерены) →
`apps`(5 обязательных APK) → `adb`(`#push FilterAppConfig.txt -> …`) →
`adb`(`pm grant`/`appops set`/`settings put`/`am start -n` — ещё 6 сырых
команд) → `instruction`(с НАСТОЯЩЕЙ картинкой из синка, не тестовой — первое
подтверждение image-фикса на реальном контенте) → `check`. Синк модели по
пути скачал реальный firmware ISO (`IVI_UPDATE_HM6W16R-V07.00.00-231010.iso`,
~700МБ) через `sync_model_payload` без сбоев — хороший стресс-тест
`content_sync.download_file` на честно больших бинарниках.

**Найден и исправлен по итогам код-ревью (без нужды в железе)**: кнопки
"Выполнить" (adb-этап) и отдельные кнопки "actions"-этапа НЕ дизейблятся на
время выполнения (специально — "actions" задуманы повторно нажимаемыми), а
`AdbSession`/`UsbFlashSession` — общие на процесс синглтоны без внутренней
синхронизации. Двойной тап (или два разных действия подряд) мог запустить
ДВА конкурентных потока команд поверх одного USB-соединения одновременно —
конкурентные `bulkTransfer` могли перепутать ответы между двумя логическими
потоками ADB. Добавлен `WebBridge.runExclusive` — простой
`AtomicBoolean`-гейт, не позволяющий двум операциям (adb_connect/
adb_run_stage/adb_install_apks/usb_connect/usb_format/usb_run_stage) идти
одновременно, с явным сообщением в лог при попытке — тот же принцип, что и
на desktop (один `adb.exe`-процесс исполняет этапы строго по очереди).

**Ещё один найден и исправлен по итогам код-ревью**: `writeFileToUsb`
(UsbFlashWrite.kt) изначально грузил весь файл в память одним
`File.readBytes()` перед записью на флешку — с ~700МБ реальным firmware ISO
из того же прогона Haval M6 это почти гарантированный `OutOfMemoryError` на
телефоне. Переписано на потоковое чтение/запись 4МБ-чанками (`InputStream` +
`UsbFile.write(offset, ...)` на каждый чанк, с логом прогресса раз в
мегабайт — тот же стиль, что уже был в `AdbInstall.syncPushBytes`). **Тот же
паттерн (`readBytes()` целиком) остался в `InstallEngine`'s `#push`/
`#install`** (ADB-путь, не USB) — там ниже риск на практике (по реальным
моделям через ADB ходят конфиги/APK, не прошивки — сама прошивка Haval M6
шла через `usb_files`, не `adb_files`), но это тот же класс проблемы, если
когда-нибудь встретится большой файл именно в `adb_files`/`#push`/`#install`
— стоит переделать таким же способом при необходимости.

**Реальные баги с реального теста (Knewstar 001, 2026-08-21)** — четыре
репорта, три воспроизведены и исправлены:

1. **Панели ADB/флешки висели на ВСЕХ этапах** (включая instruction, где ни
   то ни другое не нужно) — теперь `app.js:updateTransportBars` показывает
   каждую только для нужных типов этапа (`adb`/`apps`/`actions` → ADB-панель,
   `usb` → USB-панель), скрывая обе для остальных.
2. То же самое, отдельно отмечено техником: **ADB-панель висела на
   usb-этапе** — тот же фикс.
3. **Не показывались необязательные ("общие") приложения** — оказалось, это
   вообще не баг рендера, а ЦЕЛАЯ отсутствующая фича: desktop показывает на
   apps-/usb(`usb_copy_selected_apks`)-этапах трёхсекционное дерево
   (обязательные / необязательные модели / **общая библиотека `apk/`** по
   категориям — "Музыкальные Плееры", "Утилиты" и т.п.), а мобильная версия
   вообще не знала про общую библиотеку. Добавлено:
   [`apk_library.py`](app/src/main/python/apk_library.py) (порт
   `scanner.py:scan_apks`+`content_sync.py:list_shared_apk_catalog`/
   `ensure_apks_downloaded` — список приходит сразу дёшево из manifest.json,
   сами .apk качаются только для отмеченного, прямо перед
   adb_install_apks/usb_run_stage), `scanner_list_apks`/
   `ensure_apks_downloaded` в WebBridge.kt, и `renderApkTree` в app.js —
   общая для apps/usb этапов, коллапс-категории через `<details>`. Проверено
   на реальных данных модели — категории и remote-only-приложение ("Плеер
   AIMP (⬇ будет скачано)", имя подтянуто из .json-сайдкара) отрендерились
   верно.
4. **"Интерфейс обрезан по краям, не на весь экран"** — найдена и исправлена
   НАСТОЯЩАЯ причина, после того как техник указал точную локализацию:
   баг ТОЛЬКО на instruction-этапах (1 и 3), не на usb/apps/adb/check.
   `instruction_html` — это ПОЛНЫЙ HTML-документ своей модели
   (`<!DOCTYPE>`/`<html>`/`<head>` со своим `<style>body{margin:16px;
   background:...}</style>`, см. `cars/*/files/instruction_N/
   instruction.html`), а не фрагмент разметки. Вставлялся через
   `container.innerHTML = stage.instruction_html` — при fragment-парсинге
   `<style>` из ЧУЖОГО документа переживает вставку и его правила (в т.ч.
   `body{...}`) применяются к НАСТОЯЩЕМУ `<body>` всего приложения, а не
   только к контейнеру — на каждом instruction-этапе перекрашивало/сдвигало
   margin'ом весь экран, снаружи выглядело как чёрная рамка со всех сторон.
   Ровно поэтому баг был только на instruction-этапах — у остальных типов
   этапов нет чужого HTML-документа для вставки. (Промежуточный фикс —
   явный `WindowCompat.setDecorFitsSystemWindows` — тоже оставлен, но не
   был причиной этого конкретного бага.) Правильный фикс — то, что
   изначально и планировалось (см. старый мёртвый CSS-класс
   `.stage-instruction iframe`, оставшийся от нереализованного плана,
   и prod-комментарий В САМОМ instruction.html: "Инструкция рендерится в
   собственном `<iframe>` ... это отдельный документ" — я это прочитал в
   начале сессии, но не подключил): рендерить `instruction_html` в
   `<iframe srcdoc="...">` вместо `innerHTML` — изолирует чужой документ
   полностью, `<style>` внутри iframe действует только на его собственный
   `<body>`. Высота iframe подгоняется под контент через `contentDocument.
   documentElement.scrollHeight` на `load`. Проверено на реальных данных
   (Knewstar 001, оба instruction-этапа) — экран снова на весь экран,
   картинки внутри iframe тоже отображаются (тот же origin, WebViewAssetLoader
   работает и оттуда).

## Статус: полный самодельный ADB-транспорт + запись/форматирование флешки подтверждены на реальном железе (2026-08-21)

Реальной магнитолы под рукой нет и не будет — все тесты идут против того, что
есть: ESP32-S3 стенд (`fake_adb_device`-подобное устройство, secure=0) и
реальный Android-телефон (Redmi Note 7, Android 11, secure=1) как ADB-цель.

Подтверждено end-to-end, включая физическую установку APK на целевое
устройство (иконка появляется в списке приложений):

- **Флешка через libaums** — чтение раздела (fs/capacity/free), полное
  форматирование в FAT32 с нуля (свой writer, libaums этого не умеет — см.
  ниже отдельный раздел) и запись/чтение файлов (штатный `UsbFile` API
  библиотеки) — сразу после форматирования, в той же сессии.
- **ADB CNXN без auth** — на ESP32-S3 стенде.
- **ADB CNXN + полный RSA AUTH** (TOKEN → подпись → отклонена → RSAPUBLICKEY →
  подтверждение на экране устройства → CNXN) — на Redmi Note 7. Реализация в
  [`AdbAuth.kt`](app/src/main/java/ru/magicsqd/mobile/usb/AdbAuth.kt): RSA-ключ
  генерируется и хранится в приватном хранилище приложения, подпись токена —
  сырой `modPow` (не `Signature.getInstance("NONEwithRSA")` — этот алгоритм не
  везде доступен в штатном Android-провайдере без BouncyCastle).
- **Shell-транспорт (OPEN/WRTE/OKAY/CLSE)** — `shell:<command>` реально
  выполняется на устройстве, вывод читается корректно.
- **Установка APK по проводу** (`installApkOverAdb` в
  [`AdbInstall.kt`](app/src/main/java/ru/magicsqd/mobile/usb/AdbInstall.kt)) —
  push через классический sync-протокол (SEND/DATA/DONE, **не** sendrecv_v2 —
  v2 не существует на Android 4.4-9, целевых версиях реальных магнитол) +
  `pm install -r` через shell-транспорт. Подтверждено на полном ~49MB APK.

### Ключевые находки при отладке (даром не прошли, см. git-историю за 2026-08-21)

1. **Каждый ADB-поток обязан иметь уникальный local-id** — переиспользование
   маленьких фиксированных чисел (1, 2, ...) коллизирует с состоянием на
   устройстве, оставшимся от предыдущих подключений. Сейчас — счётчик от
   времени старта процесса (`newLocalStreamId()`).
2. **Ответы обязательно нужно фильтровать по `arg1` (получатель)**, а не
   слепо доверять "следующему пришедшему сообщению" — иначе неприбранный
   ответ от одного потока может быть принят за ответ на OPEN другого
   (`readMessageForStream`).
3. **WRTE больше заявленного в CNXN `maxdata` виснет без ответа.** Мы заявили
   `maxdata=4096` в своей CNXN — WRTE с payload'ом больше этого размера (даже
   один-единственный, даже сразу с данными) молча зависает без ответа от
   устройства на неопределённое время. Судя по всему это ROM-специфичное
   поведение (adbd буквально трактует заявленный клиентом maxdata как жёсткий
   потолок для чтения). Все sync-чанки теперь ограничены `MAX_CHUNK=3500`
   байт — с запасом под 4096.
4. **`pm install` для крупного APK может занимать больше 5с** (dexopt/
   верификация) — обычный shell-таймаут для него подняли до 120с.

На реальной магнитоле поведение USB host/adbd теоретически может отличаться
от обоих текущих стендов (особенно если там реально Android 4.4-9, а не
близкий к современному Redmi Note 7) — но раз её нет и не будет, вся
дальнейшая разработка и проверка идёт против ESP32-стенда и телефона.

## Форматирование флешки в FAT32 — подтверждено на реальном железе (2026-08-21)

`libaums` умеет читать/писать файлы на существующей FAT32, но НЕ форматирует
(`Fat32FileSystemCreator`/`Fat32BootSector` внутри неё — только `read()`, и
вдобавок помечены `internal`). Реализовали свой FAT32-writer поверх сырого
`Partition.write()` — [`UsbFlashFormat.kt`](app/src/main/java/ru/magicsqd/mobile/usb/UsbFlashFormat.kt).

- **Раскладка полей сверена byte-in-byte** с hex-дампом boot sector'а/FSInfo
  реальной флешки (~29.6GB), отформатированной проверенным сторонним
  Android-приложением из Google Play (см. `dumpRawSectors()`) — почти всё
  совпало один-в-один с первой попытки (сигнатуры, RootClus, NumFATs,
  RsvdSecCnt, Nxt_Free). Единственная реальная поправка по итогам сверки —
  таблица размера кластера (у реальных мобильных форматтеров порог проще,
  чем классическая таблица Microsoft: `>16GB → 32KB` без промежуточной
  16KB-ступени).
- **Quick format, не full format** — как и настоящие приложения (эталонное
  отработало за ~1 секунду). Пишем только boot sector+backup, FSInfo+backup
  и **первый** сектор каждой FAT-копии (три служебных записи); остальные
  тысячи секторов таблицы НЕ зануляем — на них ничего не ссылается из
  (пустого) корневого каталога. Первая версия честно зануляла всю
  FAT-таблицу и на этом либо зависала (`MAX_RECOVERY_ATTEMPTS Exceeded`
  от libaums — уже при батчах 1MB/64KB), либо работала на порядки медленнее
  реального форматтера — тот факт, что эталонное приложение уложилось в
  секунду, был прямой уликой, что оно тоже не зануляет всю таблицу.
- **Самопроверка после записи обязательна** — сразу читаем результат назад
  через тот же `Fat32FileSystem.read()`, которым пользуется всё остальное
  приложение, и только это признаём успехом (цена ошибки в форматировании
  выше, чем в ADB — испорченная ФС может потребовать ремонта через ПК).
- **Известное расхождение**: `BPB_HiddSec` у нас всегда 0, у эталона — 2048
  (1MiB-выравнивание раздела). Не подтягиваем реальное смещение сознательно —
  `PartitionTableEntry` в libaums `internal`, недоступен извне, а хардкодить
  2048 рискованно для флешек с другим выравниванием. Поле используется только
  для legacy BIOS/CHS-трансляции, современные (в т.ч. embedded Linux в
  магнитолах) ридеры его не валидируют.
- **"Флешка гаснет и пропадает после форматирования" — было симптомом
  МЕДЛЕННОЙ (полное зануление FAT) версии, не самим форматированием как
  таковым.** Контрольный тест: тем же кодом сразу после quick-format, в ТОЙ
  ЖЕ сессии без переподключения, записали и прочитали обратно тестовый файл
  через штатный `UsbFile` API — сработало за 22мс, флешка осталась в строю.
  Раньше (полное зануление, десятки секунд подряд мелких SCSI-команд) —
  либо зависало (`MAX_RECOVERY_ATTEMPTS Exceeded`), либо, судя по всему,
  именно эта долгая нагрузка и "выбивала" устройство. С переходом на quick
  format обе жалобы (медленно + отваливается) ушли одним и тем же фиксом.

## Что осталось не сделано

- **`exe`/`uart`/`telnet`-этапы не реализованы** — `exe` не имеет смысла на
  телефоне как есть (Windows-инсталлятор), `uart` требует физического
  COM-порта (маловероятно на телефоне), `telnet` в принципе возможен через
  Wi-Fi, но не сделан.
- **`adb`/`apps`/`usb`-этапы (`InstallEngine`/`writeUsbStage`) не проверены
  на реальной магнитоле/флешке** — см. секцию статуса выше.
- **`usb`-этап копирует только плоский список файлов** — `_wizard_spec.json`
  хранит `usb_files` как плоские имена (так же, как и сам desktop-визард их
  пишет), поэтому вложенные подпапки внутри `usb_files/step_N/` (если кто-то
  добавил их вручную мимо визарда) не копируются — соответствует тому, что
  реально умеет редактировать сам мастер на десктопе, не полному
  `UsbContext.copy_dir` с рекурсией по произвольной структуре.
- **`wifi_adb.py`/`telnet_adb.py`** — Windows-специфичные вызовы
  (PowerShell) внутри них нужно заменить на `WifiManager`/
  `ConnectivityManager`, если понадобится Wi-Fi ADB к самой магнитоле
  (сейчас это используется только для отладки САМОГО мобильного приложения).
- **`stages.py`/`install.py`, написанные вручную** (без `_wizard_spec.json`)
  — не покрываются интерпретатором, показывают заглушку. Полное покрытие
  потребовало бы переписать `InstallContext`/`ctx` API и исполнять эти файлы
  через Chaquopy — сознательно не делается, см. историю решения в чате.

## Как собрать

Рекомендуемый способ (Android Studio дала сбой на этом тулчейне — см. ниже) —
через командную строку, тем же способом, каким собиралось и тестировалось всё
выше:

```bash
JAVA_HOME="/c/Users/user/.jdks/jbr-21.0.11" \
  java -cp gradle/wrapper/gradle-wrapper.jar org.gradle.wrapper.GradleWrapperMain :app:assembleDebug
```

Установка/запуск на подключённый телефон:

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am start -n ru.magicsqd.mobile/.MainActivity
```

Лог приложения дублируется в logcat (тег `SpikeLog`), не нужно фотографировать
экран — `adb logcat -d -s SpikeLog:D`.

### Известная проблема с Android Studio ("Run" через IDE)

Сборка через кнопку Run в Android Studio падает с
`IllegalStateException: Current thread does not hold the state lock for root project`
— это race condition в связке Gradle Tooling API + Chaquopy при IDE-driven
сборке (есть открытый апстрим-репорт: chaquo/chaquopy#1342). При обычной
сборке через `gradlew`/`GradleWrapperMain` эта гонка не воспроизводится —
поэтому весь спайк собирался и тестировался именно так. Если нужно
дебажить через IDE (breakpoints и т.п.), возможно стоит поискать апстрим-фикс
к моменту, когда до этого дойдёт дело.

## Технологии и версии (зафиксировано на момент написания, проверить при апдейте)

- AGP 8.7.0 + Gradle 8.9 (официальная пара min/default версий) — AGP 9.x
  с "встроенным Kotlin" не смог из-за конфликта с Chaquopy 17.0
- Kotlin 2.0.21 (отдельный плагин `org.jetbrains.kotlin.android` — обязателен
  для AGP < 9.0)
- Chaquopy `com.chaquo.python` 17.0.0 (Python 3.10–3.14, minSdk 24)
- `me.jahnen.libaums:core:0.10.0` (последний релиз — 2023, но библиотека
  зрелая; альтернатив без root практически нет)
- `minSdk = 26`, `compileSdk/targetSdk = 35` — это требование к телефону
  **установщика** (современный смартфон), не к магнитоле — с ней мы вообще не
  выполняем код, только говорим по ADB-протоколу через провод.
