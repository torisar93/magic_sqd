# Magic SQD

Программа с графическим интерфейсом для установки приложений на
Android-магнитолы китайских авто — через ADB (по проводу или по Wi-Fi) или
через USB-флешку (для моделей, где ADB недоступен). Все данные (марки/
модели, инструкции, скрипты установки, стандартные APK) лежат рядом с .exe
в открытом виде и легко редактируются без пересборки программы.

Помимо Windows-версии (этот репозиторий) есть мобильное приложение для
Android (Kotlin + Chaquopy) — исполняет те же модели напрямую по USB-OTG,
без Windows-компьютера рядом. См. [`android/README.md`](android/README.md).

## Структура (то, что лежит рядом с .exe)

```
magic_sqd.exe
assets/
    icon.ico                  <- иконка окна и .exe
    splash.png                 <- картинка сплеш-скрина при запуске
tools/
    adb.exe                  <- положить сюда platform-tools (см. tools/README.txt)
    AdbWinApi.dll
    AdbWinUsbApi.dll
apk/
    yandex_navi.apk           <- любые общие APK, появятся как галочки в программе
    yandex_navi.json          <- (опц.) {"name": "...", "description": "..."}
cars/
    _shared/                  <- общий .py код для install.py/stages.py разных моделей
        load_sibling.py       <- load_install(__file__) — грузит install.py той же модели
        telnet_adb.py, wifi_adb.py  <- хелперы для подключения по сети вместо USB
    Chery/
        logo.png               <- (опц.) логотип марки — иконка слева от неё в списке "Марка"
        Tiggo 7 Pro (MTCD)/
            install.py         <- функции-этапы (см. "Контракт install.py + stages.py")
            stages.py          <- порядок этапов, обязателен — см. ниже
            files/             <- файлы для install.py (ADB-режим)
            usb_files/         <- файлы, которые копируются на флешку в "usb"-этапах
    Geely/
        Coolray (MTCA)/
            ...
```

Папки-марки, начинающиеся с `_` (например `_shared`), в списке марок не
показываются — это служебная зона.

### Необязательный слой модификаций

Главное окно выбирает модель в три шага: марка → модель → (если нужно)
модификация — единый список с breadcrumb-навигацией "назад" (см.
`app/web/frontend/js/screens/main_picker.js`). Третий шаг появляется автоматически, если у
папки модели нет СВОИХ `install.py`/`stages.py`, зато есть подпапки с ними
— удобно для рестайлингов/версий под разные рынки одной модели:

```
cars/Geely/Monjaro/
    ОД Дорест/          <- своя модификация: install.py, stages.py, files/...
    ПИ Дорест/          <- ещё одна
```

Если у папки модели есть свои `install.py`/`stages.py` прямо в ней — это
обычная модель без модификаций, третий шаг для неё не появится (ничего
менять для существующих моделей не нужно). Поле "Модификация" в мастере
"Добавить машину..." необязательно — если задано, модель сохраняется на
уровень глубже (`cars/<Марка>/<Модель>/<Модификация>/`), третий шаг
появится сам.

### Модель/модификация без известного способа установки

Если для какой-то машины ещё нет `install.py`/`stages.py`, но её всё равно
хочется видеть в списке (как "на очереди") — положите в её папку пустой
файл `no_instruction.txt`:

```
cars/Chery/Tiggo 9/
    no_instruction.txt    <- достаточно самого факта наличия файла, содержимое не читается
```

Такая модель появится в списке марка → модель как обычно, но вместо
инструкции покажет "пока нет известных способов установки" и предложит
кнопку "Сообщить о проблеме..." с уже выбранной причиной "Появился способ
установки" — то есть можно добавлять "заготовки" на будущее без похода в
редактор инструкции, просто закидывая такие файлы в папки руками.

## Добавление новой марки/модели

Проще всего — прямо в программе: кнопка **"Добавить машину..."** открывает
мастер, где этапы (включая "Инструкция" — часть инструкции с заголовками/
шагами/плашками/фото, показывается отдельной страницей на своём месте в
последовательности установки, а не единым текстом в начале), ADB-команды,
файлы для флешки и стандартный набор APK собираются без единой строчки
кода. Мастер сам генерирует `install.py` и `stages.py` в
`cars/<Марка>/<Модель>/` — их можно потом открыть и доредактировать руками,
если нужно что-то, чего нет в мастере (см. ниже контракт этих файлов). При
каждом сохранении модель автоматически уходит на сервер — сразу
публикуется (админ-сборка) или в очередь на рассмотрение разработчику
(обычная сборка, нужен настроенный `submit.json`, см. ниже).

Вручную (без мастера): скопируйте папку любой существующей модели в
`cars/<Марка>/<Модель>` и отредактируйте `install.py`/`stages.py` по
образцу (см. контракт этих файлов ниже).

## Контракт install.py + stages.py

Каждая модель — это пара файлов. `install.py` — просто набор функций
`def имя_этапа(ctx): ...`, ничего не запускает сам по себе. `stages.py`
обязателен для КАЖДОЙ модели (без него список этапов установки пуст) и
описывает порядок/тип этапов, ссылаясь на функции из своего `install.py`:

```python
# install.py
def usb_step_1(ctx):          # ctx — UsbContext, для типа "usb"
    ctx.copy_dir(ctx.usb_file("step_1"), "")
```

```python
# stages.py
import sys
from pathlib import Path
sys.path.insert(0, str(Path(__file__).resolve().parents[2] / "_shared"))
from load_sibling import load_install
m = load_install(__file__)   # грузит install.py этой же папки

STAGES = [
    {"type": "usb", "title": "Флешка — прошивка", "run": m.usb_step_1,
     "description": "Что делать пользователю на этом этапе."},
    {"type": "manual", "title": "Обновление на магнитоле"},   # run не нужен
    # "apps" сам подключается и ставит — кнопка "Начать установку" прямо на
    # этапе, отдельного "adb"-этапа после него больше не нужно (см. ниже).
    {"type": "apps", "title": "Установка приложений", "apps_connection": "wired"},
]
```

Типы этапов (`type`): `usb`, `apps` (чекбоксы APK — обязательные/
необязательные из `files/pack*/` + общая библиотека `apk/`, сам
подключается по ADB и ставит отмеченное; `apps_connection`:
`"wired"`/`"wifi"`/`"ask"` — как именно подключаться, см. ниже), `actions`
("ADB-команды" — произвольные команды по мини-DSL с необязательными
прикреплёнными файлами, `#push`/`#install` и т.п., см. `ActionSpec` в
`app/car_generator.py`), `manual`, `exe` (запуск стороннего
.exe-инсталлятора), `uart`/`telnet` (включение отладки по UART/telnet на
магнитолах, где ADB изначально скрыт), `check` (техник вручную выбирает
один из вариантов — например версию прошивки, влияет на видимость/
содержимое дальнейших этапов через `condition_var`/`condition_values` и
`variants` на других этапах), `instruction` (часть инструкции —
заголовки/шаги/плашки/фото, показывается отдельной страницей на своём
месте среди этапов установки, `run` не нужен).

`adb` — старый тип (произвольные ADB-команды без файлов), визуальный
редактор больше не предлагает создавать новые этапы этого типа (заменён
связкой "apps" + "actions" выше), но уже существующие модели с ним
продолжают работать без изменений.

### Wi-Fi ADB (модели без доступного проводного ADB)

Если у модели в принципе нет проводного ADB (магнитола сама поднимает
точку доступа или подключается к сети техника) — верхнеуровневые поля
`_wizard_spec.json`/мастера `wifi: true` и `wifi_port` заставляют ВСЕ
`adb`/`actions`-этапы модели сначала подключаться по Wi-Fi (см.
`cars/_shared/wifi_adb.py`, автоопределение IP по шлюзу → скан подсети →
ручной ввод). Для `apps`-этапа способ подключения независим от этого флага
и настраивается отдельно через `apps_connection` — так одна модель может
одновременно иметь обычные проводные `actions`-этапы и один `apps`-этап,
доступный только по Wi-Fi (или наоборот).

Оформление конкретного этапа (для любого типа, необязательно) — обычный
`description` (текст) или `"instruction": "stage1.html"` (html-файл рядом
со `stages.py`, показывается вместо `description`).

Полный список методов `ctx`:
- ADB-этапы (`InstallContext`, `app/install_context.py`) —
  `ctx.install_apk`, `ctx.shell`, `ctx.push`, `ctx.reboot`,
  `ctx.install_selected_apks()`, `ctx.ask_input(...)`, `ctx.log(...)`.
- USB-этапы (`UsbContext`, `app/usb_context.py`) — `ctx.copy_file`,
  `ctx.copy_dir`, `ctx.copy_selected_apks`, `ctx.write_text`,
  `ctx.usb_file(...)`, `ctx.file(...)`, `ctx.log(...)`.

Если что-то пошло не так — `raise Exception("текст ошибки")`, программа
покажет его пользователю и остановит установку.

### USB-флешка

Кнопка "Через USB-флешку..." (для "usb"-этапов) позволяет выбрать флешку
из списка (показываются только съёмные накопители), опционально
отформатировать (FAT32 — до ~32 ГБ, exFAT — для больших) с явным
подтверждением, и копирует файлы через `run(ctx)` этапа.

## Запуск из исходников (для разработки)

Интерфейс — pywebview (нативное окно WebView2 на Windows) + локальный
HTML/CSS/JS во `app/web/frontend/`, Python-бэкенд как раньше в `app/`
(см. `app/web/bridge.py`). Два build-варианта — техник (`main_web.py`) и
админ (`admin_main_web.py`, `admin_mode=True` — прячет adb-консоль,
показывает "Выгрузить на сервер...").

```powershell
python -m venv .venv
.\.venv\Scripts\pip install -r requirements.txt
.\.venv\Scripts\python main_web.py
```

`--admin` — временный флаг для проверки admin_mode из исходников без
сборки `admin_main_web.py` отдельным .exe. `--debug` — открывает DevTools
(консоль браузера) для отладки фронтенда.

## Сборка .exe и инсталлятора

```powershell
.\.venv\Scripts\pyinstaller magic_sqd.spec
.\.venv\Scripts\pyinstaller admin.spec
```

Собирает onedir-сборки в `dist\magic_sqd\`/`dist\magic_sqd_admin\`.
**Важно:** PyInstaller 6+ кладёт datas (в т.ч. `app/web/frontend/`) в
`_internal\` рядом с exe, а не прямо в корень — `main_web.py` учитывает
это через `sys._MEIPASS` (см. `get_frontend_dir`), `cars\`/`apk\`/`tools\`/
`assets\` пользователь по-прежнему кладёт прямо рядом с exe (это НЕ
затрагивается `_internal`, программа сама пишет/читает их по пути exe).

**Пересборка стирает `dist\magic_sqd\` целиком** — если там уже лежат
`cars\`/`apk\`/`tools\`/`assets\` (докачанные или добавленные вручную),
сохраните их перед пересборкой и верните на место после.

Дальше `installer.iss` (Inno Setup, `ISCC.exe installer.iss`) упаковывает
её в один `MagicSQD_Setup.exe` — тяжёлые `apk/`, `cars/*/files`,
`cars/*/usb_files` в инсталлятор не попадают (`Excludes` в `installer.iss`),
они докачиваются программой по требованию (см. ниже).

### Windows 7 (32-бит)

Настоящий Windows 7 не поддерживает WebView2 и Python 3.12 (см. заголовок
`installer_win7_x86.iss`) — поэтому это ОТДЕЛЬНАЯ 32-битная сборка: свой
`.venv-win7` (Python 3.8), свой вход `main_web_win7.py`, интерфейс на
PySide2/Qt5 вместо WebView2:

```powershell
.\.venv-win7\Scripts\pyinstaller magic_sqd_win7.spec --distpath dist_win7 --workpath build_win7
```

`--distpath`/`--workpath` обязательны — оба spec-файла собирают исполняемый
файл с одинаковым именем (`magic_sqd`), без явных путей x64- и Win7-сборки
затирали бы друг друга. Дальше `installer_win7_x86.iss` → `MagicSQD_Setup_Win7.exe`.

## Иконка

`assets\icon.ico` — иконка `.exe` (зашивается в файл при сборке через
`icon=` в `magic_sqd.spec`/`admin.spec`) и иконка окна во время работы
программы — обычная иконка Win32-окна WebView2, без обходных путей вокруг
переустановки иконки библиотекой (см. историю миграции: именно это
регулярно ломалось в customtkinter). Сплеш-скрин (`assets\splash.png` в
старой tkinter-версии) в pywebview-варианте пока не реализован — окно
WebView2 открывается достаточно быстро, чтобы не требовать отдельной
заглушки; при необходимости можно добавить позже.

Если понадобится заменить логотип — исходник лежит в
`assets\icon_source.png` (1024×1024). Пересобрать `icon.ico`/`icon.png` из
него (требует Pillow — `pip install Pillow`, не входит в requirements.txt,
т.к. больше не нужен самому приложению):

```powershell
.\.venv\Scripts\pip install Pillow
.\.venv\Scripts\python -c "from PIL import Image; im = Image.open('assets/icon_source.png').convert('RGBA'); im.save('assets/icon.ico', sizes=[(s,s) for s in (16,24,32,48,64,128,256)]); im.resize((256,256)).save('assets/icon.png')"
```

## Синхронизация со своим сервером (server.json / submit.json)

Тяжёлые файлы (APK, прошивки) не обязаны лежать в самом репозитории —
программа умеет тихо подтягивать их со своего сервера (см.
`app/content_sync.py`). Создайте `server.json` рядом с `main_web.py`/`.exe`:

```json
{"base_url": "https://ваш-домен/content"}
```

Это работает автоматически, без кнопок в интерфейсе, и лениво — по одному
файлу за раз, по мере реальной надобности, а не всё скопом:
- **при каждом запуске** программа обновляет скрипты моделей (`install.py`,
  `stages.py`) и список общей библиотеки APK (только имена/размеры из
  манифеста, без самих .apk);
- **при открытии модели** — только своя папка каждого `"instruction"`-этапа
  (текст+картинки видны сразу);
- **список APK apps-этапа** (обязательные/необязательные) виден сразу по
  манифесту сервера, но сами байты — только по нажатию "Начать установку";
- **файлы usb/exe-этапов** — по нажатию "Через USB-флешку"/"Запустить".

`submit.json` — куда уходит "Отправить на проверку" (мастер "Добавить
машину...") и "Сообщить о проблеме":
```json
{"submit_url": "https://ваш-домен/submit", "submit_key": "..."}
```

Если `server.json`/`submit.json` нет — вся синхронизация и кнопки
отправки просто молча пропускаются, программа работает как обычно с
локальными файлами. Серверная часть (приём заявок, админка) в этот
репозиторий не входит — приватная инфраструктура разработчика.

## adb.exe

Программа сначала ищет `tools\adb.exe` рядом с собой, и только если его там
нет — использует `adb` из системного PATH. Проще всего один раз положить
папку `platform-tools` (adb.exe + пара .dll) в `tools\` и больше об этом не
думать.
